# raylib-rs 6.0 — Roadmap & Architecture Design

- **Date:** 2026-05-25
- **Status:** Approved 2026-05-25 (signed off by repo owner)
- **Working repo:** `Dacode45/ms-raylib-rs` (personal fork)
- **Canonical repo:** `raylib-rs/raylib-rs`
- **Reference standard:** [Microsoft Rust engineering book](https://microsoft.github.io/RustTraining/engineering-book/)

This is a **top-level roadmap spec**. It fixes the cross-cutting decisions and sequences the
workstreams below. Each workstream gets its own spec → plan → implementation cycle afterward.

---

## 1. Goal

Bring raylib-rs to **raylib 6.0 parity** while:

1. Preserving the memory-safety guarantees (RAII, single-init, allocator-correct frees).
2. Making the default build depend on **nothing but raylib** — `mint`, `glam`, `serde` all become
   opt-in features.
3. Covering the **whole feature set in scope**: complete raygui, expose rlgl safely, and port **all**
   of raylib's examples to Rust as the `showcase` — which replaces `samples/` and doubles as
   integration-test material.
4. Supporting **Windows, macOS, Linux, and Web** with full CI/CD.
5. **Testing everything practical** — exhaustive coverage of window-independent functions, plus
   headless *rendering* tests enabled by the new software renderer (`rlsw`) + memory platform.
6. **House-cleaning** the backlog: triaging and incorporating open PRs/issues/community branches.

### Definition of done (whole effort)

`raylib` + `raylib-sys` at 6.0 parity, published to crates.io; default build pulls zero math/serde
deps (all opt-in and tested); raygui complete, rlgl exposed; **a comprehensive test suite —
pure/window-independent functions exhaustively unit-tested, rendering verified headlessly via the
software renderer — running green on all four platforms**; backlog triaged with attribution; a single
merge of the 6.0 branch into `raylib-rs/unstable`. **Capstone (last):** `samples/` replaced by a
`showcase/` containing all of raylib's examples ported to Rust, presented by a GitHub Pages site
deployed as the final step.

## 2. The model (Domain-Driven Design framing)

For a binding library the domain *is* the raylib API, and raylib draws the seams for us — we adopt
raysan's names rather than inventing our own (Evans, the chapter on the ubiquitous language).

### Bounded context map

```
┌───────────────────────────── raylib-sys (FFI context) ─────────────────────────────┐
│  raw bindgen surface + native #[repr(C)] math types (Vector*/Matrix/Quaternion)     │
│  invariant: layout-compatible with C; no ecosystem deps in the default build        │
└───────▲──────────────────────────────────────────────────────────────────▲─────────┘
        │ (ACL: From/Into adapters behind features)                          │
┌───────┴──────── raylib (safe context) ─────────┐         ┌─────────────────┴─────────┐
│ rcore · rshapes · rtextures · rtext · rmodels  │         │ ecosystem adapters         │
│ raudio · raymath · rlgl(safe) · collision · vr │         │  mint · glam · serde       │
│ aggregates: Image/Texture/Model/Font/Shader/…  │         │  (optional features only)  │
│ invariants: RAII teardown · single-init via    │         └────────────────────────────┘
│ RaylibHandle · !Send RaylibThread · allocator- │
│ correct frees                                  │         ┌────────────────────────────┐
└────────────────────────────────────────────────┘         │ raygui (neighbor context)  │
                                                            │  &CStr/rstr! convention     │
                                                            └────────────────────────────┘
```

- **Bounded contexts** ≈ raylib's modules: `rcore`, `rshapes`, `rtextures`, `rtext`, `rmodels`,
  `raudio`, `rlgl`, `raymath`; `raygui` is a neighboring context with its own `&CStr`/`rstr!`
  convention.
- **Invariants** (load-bearing walls): RAII `Drop` teardown (never expose `Unload*`), single-init via
  `RaylibHandle`, the `!Send` `RaylibThread`, allocator-correct frees via `ManuallyDrop<Box<[T]>>` +
  matching `Unload*`/`MemFree` (see `DECISIONS.md`).
- **Aggregates** = the RAII resource types (`Image`, `Texture2D`, `Model`, `Font`, `Shader`,
  `Material`, audio handles) — each owns a lifecycle and a consistency boundary.
- **The mint/glam/serde question is a context-boundary concern** — an anti-corruption layer between
  the FFI context and external math/serialization ecosystems (Vernon, the chapter on integrating
  bounded contexts).

> DDD artifacts (formal context files + glossary) may be formalized under `docs/ddd/` as **[DRAFT]**
> during WS0. Per the DDD change-cadence gate, finalizing them requires explicit human sign-off.

## 4. Architecture

### Crate & feature posture

Two published crates stay (`raylib-sys`, `raylib`); the **dependency posture** changes:

- **Default features pull zero math/serialization deps.** `mint`, `glam`, `serde`, `serde_json` all
  move behind off-by-default features. (Today `glam` and `mint` are mandatory — that ends.)
- **`raylib-sys` owns the math types.** It defines `#[repr(C)]` `Vector2/3/4`, `Matrix`, `Quaternion`
  matching raylib's exact layout, replacing `pub type Vector2 = mint::Vector2<f32>`. The safe crate
  re-exports these as *the* public type.
- **Feature → adapter mapping** (additive, independently composable):
  - `mint` ⇒ `From`/`Into` between native types and `mint::*`
  - `glam` ⇒ `From`/`Into` between native types and `glam::*`
  - `serde` ⇒ derives on native types (propagated into sys)

### The math decoupling (load-bearing refactor)

1. Port the **raymath** functions onto the native types as inherent methods (raylib 6.0 ships
   `raymath.h`; mirror it rather than invent). We own the math we previously borrowed from glam.
2. Replace the `MintVec2/3/4`/`MintMatrix` indirection. `impl Into<MintVec2>` call sites become
   `impl Into<Vector2>` against the native type; the optional `mint`/`glam` features supply the `From`
   impls so `glam::Vec2`/tuples/arrays keep flowing in exactly as before.
3. **Deprecation bridge:** keep `MintVec*` as `#[deprecated]` aliases to the native types for one
   release where feasible. (6.0 is a major bump, so hard breaks are allowed — the bridge is courtesy.)

### Invariants checklist (re-verified every workstream)

RAII `Drop` teardown · single-init via `RaylibHandle` · `!Send` `RaylibThread` ·
`ManuallyDrop<Box<[T]>>` + matching `Unload*`/`MemFree`. The 6.0 **skeletal-animation struct redesign**
is the sharpest risk: `Model`/`ModelAnimation` are aggregates whose `Drop` must match the new layout.

### Testability via the software renderer (`rlsw`)

raylib 6.0 ships **`rlsw`**, a CPU software-rendering backend, and a new **memory platform**
(`rcore_memory`) that runs with no window. Together they let us render into an in-memory framebuffer
and assert on the result — **rendering becomes testable in headless CI on every platform, including
web**. We expose this as a `software_renderer` Cargo feature (a backend selection, hence mutually
exclusive with the `opengl_*` features) and build the headless test harness on top of it (WS4).

Two tiers of testing follow (D10):

- **Tier 1 — pure / window-independent functions** (raymath, collision, color, easing, file/text
  parsing): unit-tested directly, no renderer needed. These start landing at WS2 and are the bulk of
  the "test everything" coverage.
- **Tier 2 — rendering correctness**: software-renderer + memory-platform integration tests that draw
  primitives and assert on the framebuffer (pixel or golden-image comparison). Unlocked at WS4 and
  used to verify WS5 (raygui/rlgl) and any drawing wrapper.

## 5. raylib 6.0 changes that hit the bindings

From the [6.0 release notes](https://github.com/raysan5/raylib/releases/tag/6.0):

- **+40 filesystem management functions** consolidated into `rcore` → affects `core/file.rs`.
- **+30 text management functions** → affects `core/text.rs`.
- **Skeletal-animation system completely redesigned** (blending within/between animations) →
  `Model`, `ModelAnimation` struct layouts change; RAII-sensitive.
- **`config.h` redesigned** (feature disabling via `-DSUPPORT_*=0`) → affects `build.rs` + feature flags.
- **High-DPI / fullscreen redesigned** (borderless-first, auto monitor scaling) → `core/window.rs`.
- **New `rlsw` software renderer** inside `rlgl` (CPU rendering, no GPU) → relevant to the safe rlgl
  module (WS4).
- **Native Win32 + Emscripten platform backends** (and a Memory backend), `utils` module removed →
  directly helps the Windows + Web platform goals.

## 6. Workstreams, sequencing & "done"

### Dependency graph

```
WS0 ─> WS1 ─> WS2 ─> WS3 ─> WS4 ─┬─> WS5 (raygui + rlgl)        ─┐
                                 ├─> WS6 (platform + CI/CD)     ─┼─> WS8 (release & merge) ─> WS9 (showcase + Pages)
                                 └─> WS7 (docs & book authoring)─┘                                    ▲ FINALE

WS0  Baseline & inventory   (triage, mise, MSRV, CI skeleton, emscripten spike)
WS1  sys 6.0 parity
WS2  math decouple
WS3  safe API 6.0 parity
WS4  software renderer (rlsw) + headless test harness     ← unlocks Tier-2 rendering tests
WS5  raygui + rlgl   (safe modules)
WS6  platform + CI/CD matrix
WS7  docs & book authoring   (built, not yet deployed)
WS8  release & merge to canonical   (crates.io publish + single merge)
WS9  showcase: ALL raylib examples ported to Rust + GitHub Pages site   ← deliberately LAST
```

The spine is **WS1 → WS2 → WS3 → WS4**: native types must exist in regenerated sys before decoupling,
the math vocabulary must settle before safe wrappers update, and the safe API must exist before the
render harness can test it. WS5/WS6/WS7 parallelize once WS4 lands; the crate **release (WS8)** needs
only those, not the full example port. **WS9 is the deliberate capstone** — replacing `samples/` with a
complete `showcase/` and deploying the GitHub Pages site that presents it. **Testing is cross-cutting**
(D10): Tier-1 unit tests land from WS2 onward; Tier-2 rendering tests are enabled at WS4 and backfilled
across drawing wrappers thereafter. (Individual showcase examples may be ported opportunistically
earlier as render-test fixtures, but the full port + public site is WS9.)

### Per-workstream done criteria

- **WS0 — Baseline & inventory.** Submodule bumped to raylib 6.0; `mise.toml`; MSRV pinned (≥ 1.85)
  and CI-verified; triaged `inventory.md` (every PR/issue/branch → merge / adapt / superseded /
  decline, with reason). Emscripten toolchain spike done here to de-risk WS6. *Done: the 6.0 branch
  builds the old API against new C, even if rough.*
- **WS1 — sys 6.0 parity.** bindgen regenerated; +40 file + +30 text symbols present; redesigned
  skeletal-animation structs land with correct layout; new `rlsw` / memory-platform symbols bound;
  `config.h` flag changes reflected in `build.rs`. *Done: `raylib-sys` compiles clean on all 4
  platforms.*
- **WS2 — Math decouple.** Native `#[repr(C)]` types + ported raymath methods; `mint`/`glam`/`serde`
  behind features; default build has zero math deps; `MintVec*` deprecation bridge; **exhaustive
  unit tests for every ported raymath method (Tier 1).** *Done: `cargo build` (no features) pulls no
  math crate; `--features glam,mint,serde` all compile + round-trip-test; math test suite green.*
- **WS3 — Safe API parity.** Every new 6.0 fn wrapped or consciously deferred; removed fns deleted;
  renamed fns deprecated → aliased; invariants re-verified against new structs; **Tier-1 unit tests
  for window-independent wrappers (collision, color, file/text parsing) as they land.** *Done: safe
  surface matches a checklist derived from `raylib.h`; audit table + Tier-1 tests committed.*
- **WS4 — Software renderer + headless test harness.** `software_renderer` Cargo feature wires
  raylib's `rlsw` backend (mutually exclusive with `opengl_*`); memory/headless platform usable from
  the safe API; a test harness that initializes a windowless context, draws into an in-memory
  framebuffer, and offers pixel / golden-image assertions; proof tests for a handful of shape/text
  primitives. *Done: Tier-2 rendering tests run green headlessly on all desktop platforms and the
  harness builds for web.*
- **WS5 — raygui + rlgl (safe modules).** raygui at 6.0 parity; safe rlgl module (incl. how `rlsw`
  surfaces); **raygui & rlgl drawing verified via the WS4 harness.** *Done: raygui + rlgl wrapped and
  render tests cover the new modules.*
- **WS6 — Platform + CI/CD.** Matrix (Win/macOS/Linux build + test headless; web build verified
  continuously); the `software_renderer` Tier-2 tests run across the matrix; fmt + clippy `-Dwarnings`
  + `deny(missing_docs)` + doctests + cargo-deny + MSRV all gating; sanitizers informational. *Done:
  matrix green and gates actually fail on violation.*
- **WS7 — Docs & book authoring.** mdBook content with per-platform build guides written and building
  in CI; `CHANGELOG.md` + version numbers synced. *Not deployed yet — public deployment is WS9.*
  *Done: book builds clean; content complete.*
- **WS8 — Release & merge.** Tag; publish `raylib-sys` then `raylib` to crates.io; single merge of the
  6.0 branch into `raylib-rs/unstable`. *Done: 6.0 on crates.io; canonical has the merge.*
- **WS9 — Showcase + GitHub Pages (FINALE).** `samples/` removed; `showcase/` holds **all** of
  raylib's examples ported to Rust (`showcase/original` C → `showcase/src/example` Rust), building on
  desktop and to wasm where applicable; the GitHub Pages site (book + showcase gallery with embedded
  wasm demos) is assembled and **deployed** as the last step. Workspace `exclude`/members updated to
  drop `samples`. *Done: `samples/` gone, every raylib example ported and building, and the Pages site
  is live presenting the showcase.*

## 7. CI/CD architecture

Replace the two thin workflows (`ci.yml` Ubuntu-only doctests, `rust.yml` Ubuntu build) with a layered
set:

- **`check.yml`** (fast, every push/PR): fmt `--check`, clippy `-Dwarnings`, `deny(missing_docs)`
  build, cargo-deny (license allowlist + RUSTSEC advisories), MSRV build. No window needed.
- **`test.yml`** (matrix): `{ubuntu, macos, windows} × {default, no-default-features, all-features,
  software_renderer}`; unit + doctests on all; the **`software_renderer` variant runs the Tier-2
  headless rendering tests** on every OS (no GPU/window needed); Linux additionally runs the
  window-opening integration tests under **xvfb**.
- **`web.yml`**: `wasm32-unknown-emscripten` build of lib + showcase examples (and a
  `software_renderer` build to prove the headless path compiles for web) — **build-verified
  continuously**. The **public GitHub Pages deploy of the showcase site (book + gallery) is gated to
  the WS9 finale**, not run on every push.
- **`release.yml`** (tag-triggered): verify version/CHANGELOG sync; `cargo publish` sys then safe;
  create GitHub release.
- **`sanitizers.yml`** (informational, `continue-on-error`): ASAN/UBSAN over FFI-heavy tests.

## 8. Top risks & mitigations

1. **bindgen drift on 6.0** — new backends/structs may break generation per-platform. *Mitigation:* the
   existing `nobindgen` / `RAYLIB_BINDGEN_LOCATION` escape hatch for manual auditing.
2. **Skeletal-animation layout** — wrong `Drop` = use-after-free. *Mitigation:* a focused RAII test per
   redesigned struct.
3. **Emscripten in CI** — toolchain setup is fiddly. *Mitigation:* WS0 spikes it early rather than
   discovering it at WS6.
4. **`rlsw` + memory platform maturity** — the software renderer and windowless platform are new in
   6.0 and may have gaps or platform quirks. *Mitigation:* WS4 validates the exact headless mechanism
   (memory platform vs render-texture readback) before committing the test harness to it.
5. **Big-bang merge** (chosen model, D5) — review/merge risk. *Mitigation:* per-workstream commit
   groupings + keep the 6.0 branch rebased on `unstable`.
6. **Doc-gate friction** — `deny(missing_docs)` over a large surface is a lot of writing.
   *Mitigation:* introduce the gate incrementally per module as WS3/WS4 land, flip to deny once clean.
7. **Full example-port volume (WS9)** — raylib ships well over a hundred examples; porting all is
   large. *Mitigation:* it's the deliberate finale, parallelizable, and seeded by examples already
   ported as render-test fixtures + the salvaged `samples/`, `sola`, and `samples/*` branches (D6).

## 9. Open questions for later workstream specs

- Exact MSRV floor (1.85 vs a slightly higher, more comfortable version).
- Headless render-test mechanism — memory platform vs render-texture readback — and pixel-tolerance
  vs golden-image assertions (validated in WS4).
- Whether the deprecation bridge for `MintVec*` is worth maintaining given a major bump, or dropped.
- crates.io publish ownership/tokens for the release pipeline.
